# Ether Tarot 手势抽牌交互与牌堆界面设计

日期：2026-08-08  
状态：已确认

## 1. 背景与目标

当前版本已经实现 78 张塔罗牌、MediaPipe 单手识别、Three.js 牌堆、捏合抓牌、拖拽、握拳确认、正逆位结果和鼠标备用模式。此次优化不以修复功能故障为目标，也不预设当前手势识别不稳定。

本次设计解决的核心问题是产品交互的可发现性和反馈闭环：

- 深灰牌堆与黑色背景对比不足，用户无法快速判断牌堆位置。
- 牌堆靠近画面下方，且缺少标签、轮廓和引导。
- 用户看得到手势状态，但不容易判断是否已经瞄准、抓取成功或可以确认。
- 握拳同时承担确认和化灰，动作结果难以预判。
- 当前流程对短暂丢失手部、误操作和移动端布局缺少明确恢复策略。

目标是让首次使用者无需阅读长说明，也能发现牌堆并完成一次完整抽牌，同时保留现有随机抽牌逻辑和三种基础手势。

## 2. 设计原则

1. 功能逻辑不变：任意一次成功抓牌仍从同一套剩余牌库中随机抽取。
2. 牌堆优先：空闲状态下，牌堆是画面的唯一主要视觉焦点。
3. 状态可见：每个手势动作都必须产生及时、明确的视觉反馈。
4. 动作可预期：确认和结束不得共享含义含混的不可逆操作。
5. 异常可恢复：短暂丢失手部不能立即导致卡牌丢失或流程重置。
6. 输入一致：手势、鼠标和触摸复用相同的交互状态和视觉反馈。

## 3. 现状差距

### 3.1 牌堆不可发现

当前牌堆位于 Three.js 世界坐标 `(0, -2, 0)`，材质基础色为 `#333333`，背景接近黑色。牌背纹理来自外部 URL；纹理加载失败后，画面上只剩一个低对比度深灰薄盒。界面仅显示剩余牌数，没有把该数值与场景中的具体牌堆建立视觉联系。

### 3.2 交互反馈不完整

当前光标会根据 OPEN、PINCH、FIST 改变颜色，但缺少以下反馈：

- 光标是否命中牌堆；
- 牌堆是否已经可以抓取；
- 捏合是否成功创建了卡牌；
- 卡牌应被拖到哪里；
- 何时允许确认；
- 手部丢失后系统会如何处理。

### 3.3 动作语义冲突

握拳同时用于确认和化灰。用户无法仅通过动作预测系统会展示结果还是销毁卡牌，不符合动作与结果一一对应的交互原则。

## 4. 选定布局：中央祭坛

空闲状态采用“中央祭坛”布局：

- 牌堆放置在画面中心略偏下的位置，不再贴近底部。
- 牌堆视觉尺寸相对当前版本放大约 15%。
- 使用 3–5 层轻微错位的卡片表现厚度，而不是单个薄盒。
- 采用项目内置牌背资源，避免核心视觉依赖外部热链。
- 增加金紫色描边、柔和呼吸光和低幅度上下浮动。
- 牌堆下方固定显示“命运牌堆 · 剩余 78 张”。
- 首次空闲提示为“将手移向牌堆”。

牌堆必须在牌背纹理尚未加载时仍保持高可见度，因此颜色、轮廓、标签和层叠结构不能依赖纹理成功。

## 5. 完整交互流程

主流程为：

`寻找牌堆 → 瞄准 → 捏合抓牌 → 拖到揭示区 → 握拳确认 → 翻牌展示`

### 5.1 寻找牌堆

- 中央牌堆保持柔和呼吸光。
- 页面显示“将手移向牌堆”。
- 手势光标可见，但不抢夺牌堆的视觉焦点。

### 5.2 瞄准

- 光标命中牌堆后产生轻微吸附。
- 牌堆上浮并增强外发光。
- 文案切换为“捏合抓取一张”。
- 未命中牌堆时，捏合不触发抽牌。

### 5.3 抓牌

- 检测到有效捏合后，从牌堆顶部视觉分离一张卡牌。
- 只有在此刻才从剩余牌库中随机取牌。
- 使用短促光效确认抓取成功。
- 牌堆计数立即更新。

### 5.4 拖拽

- 画面中央出现半透明揭示区。
- 卡牌跟随光标移动，并保留适量平滑以减少视觉抖动。
- 卡牌靠近揭示区时产生磁吸和高亮。
- 牌堆在此阶段降低亮度，避免与手中卡牌竞争。

### 5.5 确认

- 只有卡牌进入揭示区后才允许握拳确认。
- 握拳后显示约 500ms 的环形确认进度。
- 确认过程中松开拳头会取消进度，卡牌保持在揭示区。
- 握拳只承担确认职责，不再触发化灰。

### 5.6 翻牌与结束

- 确认完成后执行翻牌动画，展示牌面、正逆位、牌名和含义。
- 用户可选择“收下这张牌”或“重新抽取”。
- 如果保留化灰效果，它只能作为明确标注的结束动作出现，不能复用握拳确认。

## 6. 手部丢失与错误恢复

- 手部短暂消失时，卡牌停留在最后位置，不立即返回牌堆。
- 手部连续消失约 1 秒后，卡牌平滑返回牌堆并取消本次未完成抓取。
- 重新检测到手部后，从中性状态恢复，不能继承上一次捏合或握拳状态。
- 摄像头权限被拒绝、摄像头不可用或模型初始化失败时，自动进入鼠标/触摸模式，并显示可操作的原因说明。
- 页面切换到后台时暂停视觉推理；返回前台后重置瞬时手势状态。

## 7. 手势稳定性边界

本次工作不把“识别稳定性改造”作为独立目标。只有测试发现真实误触或抖动时，才引入以下最小机制：

- 候选手势保持 150–250ms 后确认；
- 捏合进入和释放使用不同阈值，避免阈值边缘反复跳变；
- 坐标采用轻量平滑，但不能导致明显拖尾；
- 握拳确认使用约 500ms 驻留进度。

这些机制服务于交互容错，不改变现有 MediaPipe 技术选型，也不要求训练自定义模型。

## 8. 桌面端结果布局

- 翻牌后，卡牌占据中央主视觉区域，宽度约为视口高度的 28–34%。
- 牌名、正逆位和核心含义显示在卡牌右侧，不覆盖卡牌。
- 左上角手势说明在首次成功抽牌后自动折叠，只保留模式切换入口。
- 右上角仅保留摄像头状态、当前手势和剩余牌数。
- 底部抽牌历史改为可折叠抽屉。
- 结果状态下弱化或隐藏牌堆，突出本次牌面。

## 9. 移动端布局

- 牌堆位于中央偏上，避开浏览器底部工具栏和安全区域。
- 结果使用纵向布局：卡牌在上，牌义在下。
- 手势模式提供可隐藏的摄像头预览小窗。
- 模式切换、重抽和结束按钮位于底部安全区域。
- 所有触控目标的最小尺寸为 44px。
- 性能不足或摄像头不可用时，自动降级为触摸拖拽。

## 10. 视觉系统

- 背景：近黑紫色，维持现有神秘氛围。
- 牌堆与主要动作：金色，作为主视觉层级。
- 手势光标与识别反馈：青紫色。
- 成功状态：绿色。
- 暂时失去追踪或需要用户注意：琥珀色。
- 错误状态：红色，仅用于真正失败。

不能只依赖颜色表达状态；关键状态同时使用文字、形态变化或进度动画。

## 11. 组件边界

实现时应把当前单文件中的职责拆成可独立测试的单元：

- `GestureInput`：输出中性的指针、手势和可见性事件。
- `InteractionStateMachine`：管理空闲、瞄准、抓牌、拖拽、可确认、揭示和结果状态。
- `DeckView`：负责牌堆层叠、发光、计数和命中反馈。
- `CardView`：负责卡牌跟随、吸附、翻牌和结果动画。
- `GuidanceUI`：根据状态显示下一步提示和异常说明。
- `ResultPanel`：展示牌名、正逆位、牌义和后续动作。

鼠标、触摸和手势输入只能通过统一事件驱动状态机，不能各自复制业务规则。

## 12. 验收标准

### 可发现性

- 新用户进入页面后 3 秒内能指出牌堆位置。
- 牌背纹理加载失败时，牌堆仍清晰可见并可操作。
- 剩余牌数与牌堆形成明确视觉关联。

### 完成度

- 用户不阅读长说明也能完成一次完整抽牌。
- 寻找、瞄准、抓牌、拖拽、确认和结果状态均有可见反馈。
- 抽出的牌仍来自同一剩余牌库，且牌数只在抓取成功后减少一次。

### 容错

- 短暂丢失手部不会立即丢牌。
- 握拳在揭示区外不能确认。
- 确认驻留未完成时松拳不会触发翻牌。
- 摄像头不可用时仍可通过鼠标或触摸完成完整流程。

### 响应式

- 从桌面宽度缩放到手机宽度时，控件不遮挡牌堆、手中卡牌或结果内容。
- 移动端主要触控目标不小于 44px。

## 13. 非目标

- 不更换或训练新的手势识别模型。
- 不增加新的塔罗牌阵和占卜主题。
- 不改变随机抽牌、正逆位和剩余牌库规则。
- 不在本阶段实现账号、云同步、分享或社交功能。
- 不进行与本交互流程无关的全面视觉重构。
